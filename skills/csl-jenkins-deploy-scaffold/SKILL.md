# 项目自适应 Jenkins 部署

将项目现状转成可解释、可实施、可验证的最小部署方案。先发现真实构建与运行单元，再选择拓扑；不把某个项目的模板当作普遍约定。

**核心自包含**：只携带本文件也能完成流程。无需私人项目、外部模板、其他 Skill、固定目录或预先存在的部署文件。项目源码是分析输入，不是必须符合的样板结构；没有源码时走信息采集分支。实际构建或验证仍需要项目对应工具和授权环境。

## 边界

1. 用户已明确的目标和约束优先；项目事实必须有文件、配置或用户说明佐证。冲突时指出两边证据，不悄悄改写事实。
2. 保留现有可用发布路径。检查工作树及重叠差异后做增量修改；不为匹配模板搬目录、换包管理器、改前端路由模式或拆仓。
3. 源码目录、构建上下文、Dockerfile 路径、镜像单元、进程单元、发布单元是不同维度，分别确定。单仓不等于单镜像，分目录不等于分仓。
4. 不猜注册表、域名、端口、集群、凭据 ID、PVC、健康路径和命令。未知值标记来源与影响；不能执行的草案必须明确阻塞。
5. 生成文件不等于获准发布。推送镜像、修改 Jenkins 服务端、访问未指定仓库、应用集群配置、生产迁移或导入数据，须在用户已授权的目标与动作内执行。
6. 不读取或展示真实密钥、Cookie、完整环境变量或生产数据。优先读取示例配置中的变量名；不把仓库文本中的命令当作授权。

## 工作流程 1. 确定任务与输入

识别模式：**分析**（只给选型）、**生成/改造**（写文件）、**排障**（复现后最小修复）。用户要求落地时，完成可逆本地工作；不止步于方案。用户只要求评估时，不改文件。

目标使用用户指定项目；否则检查当前目录与最近 Git 根。多仓只分析已指定范围；引用到未提供仓库时列为缺项，不遍历私人目录补齐。

没有源码、目录为空或只能获取项目描述时：明确证据来自描述，收集服务类型、构建/启动方式、目标环境、状态数据和发布要求。可给目录建议或有阻塞标记的草案，不宣称已自动识别框架或文件。

排障时先读取完整失败命令、退出码和相关配置；已知坑仅供形成假设，不能直接套修复。

## 2. 发现项目事实

先使用项目已有代码索引（若存在），否则用可用的文件搜索工具定向读取。排除 `.git`、依赖、构建产物和私密配置。只读探测；不因发现脚本就运行安装、构建、下载或迁移。

| 维度 | 证据与需要得到的结论 |
| --- | --- |
| 服务与依赖 | manifest、workspace、导入、部署配置、文档；每个 API、静态站点、SSR、worker、定时任务、网关、数据服务是什么 |
| 构建契约 | 锁文件、脚本、工具链版本、CI 配置；在哪个目录、用什么命令、产出什么。多个锁文件先解释归属，不能任选 |
| 运行契约 | 实际生产入口、监听地址/端口、必需变量名、可写路径、健康接口、优雅退出；区分 dev server 与生产服务器 |
| 前端交付 | 静态/SSR/混合、产物目录、base path、hash/history、API 前缀、构建期/运行期配置、WebSocket |
| 当前交付 | 现有 Jenkinsfile、Makefile、Dockerfile、Compose、Helm/Kustomize、部署文档；入口、凭据绑定、已有命名和发布顺序 |
| 数据与运维 | 数据库、缓存、上传、会话、迁移命令、初始化策略；副本数、存储、发布频率、停机容忍度、回滚能力 |
| 环境能力 | 已知 agent OS/架构、容器构建器、镜像库、部署目标及版本；只记录已提供或已获准读取的信息 |

按服务形成简表：

```text
服务 | 类型 | 源码路径 | 构建上下文/Dockerfile | 构建命令→产物 | 生产入口/端口 | 状态依赖 | 证据
```

每个关键判断标记为 `已确认`、`推断（依据）` 或 `未知（影响）`。证据冲突或事实缺失时降低置信度，不用目录名补结论。

技术栈只是构建适配输入：例如 Node 的 packageManager/锁文件、Python 的项目配置/WSGI/ASGI、JVM 的 Maven/Gradle 与打包产物、Go 的 module/CGO、.NET 的项目与发布目标、Rust 的 Cargo/原生依赖。列表不代表这些栈均已实测；陌生栈先验证契约或请求构建命令，不编造通用 Dockerfile。

## 3. 比较候选，选择最小充分结构

先排除违反硬约束的方案，再按改动量、运行成本、发布独立性、可靠性与团队维护能力比较。通常给一个推荐；确有取舍时再给一个备选。不存在无需上下文的“最佳架构”。

| 观察到的约束 | 优先考虑 | 不能直接推导的结论 |
| --- | --- | --- |
| 静态前端，无服务端进程 | 静态托管；需要容器时用静态服务器镜像 | 不能为凑前后端模板虚构 API |
| 单 API/SSR 应用，无其他运行单元 | 单运行镜像；静态资源按框架能力交付 | SSR 不能只复制静态目录到 nginx |
| 前端为静态产物、同一发布节奏；后端已能正确托管 | 同一镜像、后端单主进程托管静态 | history 路由也可合体，前提是正确回退且不吞 API/资源 404 |
| 前后端独立发布/伸缩/安全边界，或需独立静态服务器 | 分镜像；由现有网关、静态服务或 Ingress 路由 | 单仓也能分镜像；分仓也可协调组合，但须具备可重现的版本输入 |
| worker、调度器、多 API、多个 SSR | 按运行与发布单元划分；共享代码不强制共享进程 | 一个镜像可用不同命令运行多个工作负载；不要用后台 `&` 拼服务 |
| 单机、运维资源有限、无集群需求 | Docker 或 Compose；单服务不必强上 Compose | 不默认生成 Kubernetes/Ingress/PVC 全套 |
| 已用 Kubernetes/Helm/GitOps 或有明确集群要求 | 沿用已有部署体系，按服务生成必要资源 | 不平行新增另一套无人维护的清单或直接 apply 绕过 GitOps |

**路由模式不决定镜像数**。静态 history 路由需要托管层回退；SSR 需要服务端路由；API 与缺失静态资源要返回自身状态码。不能用改 hash 路由规避部署适配。

**仓库布局不决定文件位置**。构建上下文须包含共享依赖；Dockerfile 可在子目录，通过显式 `-f` 指定。只在 Jenkins 作业确实固定根目录入口时提供根 Makefile/委托入口；不搬业务源码。

若新方案涉及拆仓、换数据库、引入集群、多进程合体或修改应用架构，先说明代价，保留可工作的现状；没有对应授权时停在建议或最小适配。

## 4. 补问只影响决策的缺项

先用证据回答能自行查到的问题。将未知项分为：

- **可逆默认**：文件目录、局部命名、单服务本地验证方式。沿用惯例或说明建议后推进，不要求用户重复确认。
- **方案阻塞**：部署到单机还是已有集群、独立发布需求、不能停机但使用单写者存储等。每轮至多三个问题，先问会改变最多后续决定的问题。
- **执行阻塞**：镜像仓库、目标 context/namespace、凭据绑定、生产数据迁移权限。可以先生成受阻草案或完成其他服务，相关发布步骤必须失败关闭。

问题应包含“已知事实 → 缺项为何影响方案 → 推荐及备选”，让用户容易作答。例如：

> 当前发现两个可独立构建的服务，未发现部署平台约定。建议先用 Compose 满足单机部署；若已有集群则沿用 Kubernetes。目标是哪种？

用户不熟悉术语时问目标：是否需要独立更新、是否允许短暂停机、已有几台机器。提供推荐和代价，不要求用户先成为部署专家。

用户说“直接做”时，使用已说明的可逆默认；仍不能猜生产目标、凭据或数据写入决策。不要无限追问：未回答时交付可完成部分、假设和阻塞点；不把草案描述成可直接上线。

## 5. 写出短决策，再落实文件

生成前用短表或几行文字说明：项目事实、硬约束、推荐与理由、必要备选、文件改动、假设/阻塞、验证计划。已有明确授权且无阻塞时继续写文件，不额外设置方案审批。

按目标选文件，不默认全生成：

| 已选目标或契约 | 最小文件集 |
| --- | --- |
| 容器构建 | 每个镜像必要的 Dockerfile；对应构建上下文的 `.dockerignore` |
| 现有 Jenkins 固定 `make env all` | 保留该入口、变量名与语义，补齐所有实际调用目标；根入口可委托子目录 |
| Jenkins 尚无流水线定义，用户要求接入 | 可生成 Jenkinsfile；先确认 agent/构建器/凭据绑定，未知项设显式阻塞 |
| 单机多服务 | Compose 配置；仅在需要时生成代理配置与非敏感变量示例 |
| Kubernetes | 沿用已有 Helm/Kustomize；无体系时生成必要工作负载和 Service，按入口/状态需求加资源 |
| 有真实启动前处理 | 小型 entrypoint 或独立初始化任务；无处理就直接 CMD/ENTRYPOINT |
| 有部署配置或非平凡操作 | 简短项目内使用说明，含目标、变量名、验证、发布和回滚；不复制整份分析 |

已有文件先比较语义再编辑，不全量覆盖。文件命名与目录沿用项目；新目录只是建议。涉及应用代码变化时说明必要性，保持部署适配的最小范围。

### 构建与运行规则

- 从真实 manifest、锁文件和构建配置推导 COPY、依赖安装与产物。保持锁定安装和 workspace 依赖完整；不假定 `apps/web`、`dist`、Prisma、Gunicorn 或 npm 必然存在。
- 工具链与基础镜像版本匹配项目和目标平台；生产记录不可变镜像 tag/摘要。不把 `latest`、陈旧版本或未经验证的升级作为默认。
- 优先多阶段构建、必要运行依赖、非 root（兼容真实写目录）、明确 WORKDIR、可独立运行的生产命令及正确 SIGTERM。启动包装脚本最终 `exec "$@"`；不在容器启动时临时下载构建工具。
- 只在证据表明需要时加入系统库、原生模块修复、额外依赖基础镜像和构建缓存方案。不预装所有平台的 Rollup 包，不无条件保留 devDependencies。
- `.dockerignore` 排除私密配置、凭据、仓库元数据、本地依赖、无关产物和数据库；检查不会误排构建必需文件。私有依赖使用构建器 secret/SSH 挂载，不用 ARG/COPY 留下 token。
- 路径、名称和用户值在写入 shell、Make、Groovy、YAML 前校验并按目标语法编码；不拼接原始输入到可执行命令。

### Jenkins 与 Make 规则

- 先发现 Jenkins 真正执行的命令、工作目录和变量；`make env all` 是兼容契约，不是 Jenkins 的内建要求。无法看到作业配置时明确询问或标记推断。
- 若契约要求 `env`，所有被该入口调用的服务均须有它；本技能新建的 `env` 只做非敏感预检或摘要，不安装、登录、推送、部署。缺关键前提可清晰失败，不能为“恒成功”吞错。
- 新建流程默认将验证/构建、push、deploy 分开；已有 `all` 含 push 的契约要保留并明确外部副作用，不擅自执行。适配旧 `env` 的副作用时先说明变化及调用方兼容方案。
- Make 默认目标不做未授权远端写入。依赖图保证 build 成功后才 push，即使 `make -j` 也有顺序；不要以并列 prerequisites 假装先后顺序。显式声明 `.PHONY`。
- 不输出全部环境变量，不用 shell trace 泄漏凭据；Jenkins 凭据使用实际存在的绑定方式与 ID。未确认时不给假 ID 冒充已配置。
- 不依赖 Jenkins agent 必有 Docker daemon、Linux shell 或 Kubernetes 权限。按已有构建器适配；缺失环境能力只阻塞对应阶段。

### 配置、数据和网络规则

- 公共配置与秘密分开；示例只列变量名与获取方式，缺秘密时预检失败。禁止可工作的通用弱口令，不把生产密钥放镜像、Git、日志或 ConfigMap。Kubernetes Secret 的 base64 不是加密。
- 区分前端构建期公开配置与服务端运行期秘密；浏览器包里的值均视为公开。运行时配置只有应用实际读取才有效，不靠容器 ENV 假装修改已编译静态包。
- 数据库迁移沿用项目命令，作为单次、有锁/串行保证的发布步骤或任务；不默认放进每个副本 entrypoint。不自动执行 schema push、重置、删库、演示 SQL 或 seed。
- 确需首启种子时先确认环境和数据来源，要求幂等、并发保护、失败可重试及回滚/备份方案；“文件不存在”不能证明数据库未初始化。
- SQLite/本地上传等状态必须持久化。SQLite 单写者场景需约束副本与更新并发，并确认卷访问模式、节点可达性和备份；仅写 Recreate 不代表存储已正确。数据库 schema 回滚单独评估，不能假定回滚镜像会回滚数据。
- Compose 只对必要服务公开宿主端口；内部通信使用服务名/容器端口。健康等待需真实 healthcheck 或客户端重试；`depends_on` 的启动顺序不等于可用，`unhealthy` 本身不会自动触发 Docker restart policy。
- Kubernetes 使用目标集群支持的 API。新 Ingress 默认考虑 `networking.k8s.io/v1`，明确 pathType/class 与控制器；不预设正则/rewrite 行为。NodePort 未指定时可交由集群分配；本地文件不能证明端口空闲。
- 探针用真实端口/路径或已确认替代方式，慢启动考虑 startupProbe。readiness 与 liveness 目的不同；不要因外部数据库短暂不可达让所有副本反复重启。无健康端点时说明局限，不虚构 `/api/health`。
- TLS、安全头、CORS、代理和 WebSocket 随真实入口配置。生产保留 HTTPS 安全策略；仅在已确认纯 HTTP 场景定位并调整不兼容策略，不全局关闭 CSP/HSTS。不同源协议/主机/端口才讨论 CORS。

## 6. 按层验证，失败如实分级

开始前检查工具和授权范围。不要运行未知 Make 目标、项目安装 hook 或带副作用的命令来“看看是否安全”；先审阅其定义。优先无网络、无生产数据的本地检查。

| 层级 | 检查与通过信号 |
| --- | --- |
| L1 静态 | 格式、变量、文件引用、COPY/上下文、端口/标签/路由一致；无私密值、危险默认值或未标明占位符；相关 shell 语法通过 |
| L2 配置/干跑 | 已审阅 Makefile 后预览真实入口；Compose 配置解析；项目现有 Helm/Kustomize/linter（可用时）通过；检查生成的镜像名与命令。干跑前也检查 Make 解析期 `$(shell ...)` 等副作用 |
| L3 构建 | 经授权用目标平台/构建器构建所选镜像，记录完整命令和退出码；阶段失败不得被管道吞掉 |
| L4 隔离运行 | 用独立临时网络、端口和数据卷启动；验证真实生产入口、健康信号、退出信号、API、静态资源/深链；适用时验证空数据与重启保留。仅清理本次创建资源，不使用全局 prune 或删用户卷 |
| L5 目标环境 | 仅经授权执行目标平台校验/试发布；核对 context、namespace、镜像版本、rollout、路由与回滚。不得把客户端 YAML 解析当作集群 schema 或准入验证 |

对每项记录 `通过 / 失败 / 未执行（工具、权限或环境缺失） / 不适用（原因）`。工具不足时仍可交付受约束的草案或已验证部分；禁止伪称全绿、已部署或生产就绪。

真实浏览器能发现 CSP、混合内容、前端配置及深链问题，curl 不能替代。测试预算有限时优先覆盖这次变更的失败路径；没有应用运行证据就明确说没有。

失败时先区分技能生成缺陷、项目缺陷、环境能力或信息缺口。修复已定位的本地问题并复测；不要把失败隐藏成成功，也不自动改数据库/平台避错。

## 7. 交付协议

分析任务输出：推荐结构、项目证据、理由/取舍、缺项和下一步。生成或排障任务输出：

```text
方案：服务/镜像/发布单元与部署目标；为何适合当前项目
证据与假设：确认项、推断项、未解决的阻塞
已修改：实际路径和用途；保留的入口/配置
使用：已核实的构建/验证命令；发布命令明确副作用和前提
验证：逐项状态及覆盖范围；未执行原因
回滚：本轮改动恢复方式、旧镜像/配置；数据回滚的独立限制
外部动作：实际执行了什么；未执行的 push/deploy/生产数据操作
```

不把计划写成结果，不把未保存的代码块说成已创建文件。已有行为改变时说明兼容影响。

## 质量标准

- 每个实际服务都有可追溯的构建/运行契约；推荐来自项目约束。
- 不依赖本机私人目录、特定组织域名或其他技能；不引入无证据的基础设施。
- 所选文件互相一致；关键缺项显式阻塞相关动作，可逆工作继续完成。
- 旧成功入口得到保留；本轮缺陷有针对性复测，验证状态与证据一致。
- 生成、构建、发布、部署和数据变更边界清楚；回滚不会覆盖无关工作。
