# 部署故障：证据、原因与最小修复

可选诊断参考。保留旧版的问题类型，移除私人项目路径与组织约定；不把个别事故当作所有项目的根因。先确认实际命令、退出码、运行环境，再采用对应修复。以下不是本轮真实项目实测报告。

## 1. 浏览器白屏，curl 返回 200

检查浏览器控制台与 Network：资源 URL、MIME、CSP、混合内容、base path、API 配置、运行期错误。curl 不执行浏览器安全策略或 JavaScript，不能证明页面可用。

只有确认站点仅提供 HTTP、且 CSP `upgrade-insecure-requests` 导致资源升级失败时，才对该环境调整相应策略。HSTS 有独立适用条件；不要把它与任何 HTTP 白屏都视为同一个原因。生产 HTTPS 入口保持合理安全头，不一并关闭 CSP、HSTS、认证或 CORS。

修复后验证真实页面、资源和业务请求；没有浏览器条件时明确留下证据缺口。

## 2. Rollup 或其他原生依赖缺失 / EBADPLATFORM

先检查锁文件、包管理器版本、optional dependencies 设置、实际目标 OS/CPU/libc，以及是否从宿主复制了 node_modules。

- Debian/Ubuntu 通常是 glibc，对应 `gnu`；Alpine 通常是 musl。Debian 不是 musl 系统。
- 多架构构建中构建阶段和目标运行阶段可能不同，不能无条件用构建机 `uname` 代表目标平台。
- 优先按项目约定在目标容器内进行锁定安装，核实当前包管理器已知问题与锁文件覆盖。
- 只有已定位为对应版本的原生 optional 包漏装，才补装与该依赖版本及目标平台匹配的包，并验证没有改坏锁文件。

不要同时安装所有 CPU/libc 变体，不删除锁文件逃避问题，不把一次临时补装写成每个项目的默认步骤。

## 3. `make: No rule to make target 'env'`

确认 Jenkins 的实际入口、工作目录、`-f` 参数及委托 Makefile；并非 Jenkins 天生需要 env。

若入口确实是 `make env all`，所有被调用的实际服务入口都补齐 env。新目标只预检/打印非敏感摘要，关键前提缺失应失败；不靠吞错维持假绿，也不把 push 放入 env。

审阅 Makefile（包括解析期 shell 调用）后再运行无外部副作用的预检或干跑。若现有 all 会推镜像，不以“验证”为由直接运行。

## 4. 静态文件存在，但访问 404 或深链失败

核对最终镜像中的真实绝对路径、WORKDIR、构建产物、base path 与服务器配置。`__dirname` 所在层级由实际编译产物决定，不复制固定 `../../../public`。

history SPA 的回退可放在现有后端、静态服务器或网关，不强制分镜像或改 hash。确认 API 和缺失资源仍返回正确的 404；若 JS 请求返回 HTML，修复路由匹配，不把状态 200 当成功。

SSR 使用实际服务端路由，不能以静态 fallback 代替。

## 5. 开发运行成功，生产启动失败 / NestJS 注入异常

先核对正式构建与生产入口、编译器和装饰器元数据配置。部分依赖装饰器元数据的 NestJS 应用不能直接用 tsx/esbuild 代替原生产编译链。

使用项目真实生产命令复测，不预设所有应用产物都是 `dist/main`。纯数据脚本是否可用 tsx，取决于其依赖和运行时能力；不能据此要求生产镜像保留所有开发依赖。

## 6. 日志看似成功，命令实际失败

检查命令退出码与管道传播。不要只看日志末尾或匹配“成功”文字。

POSIX sh 不保证支持 pipefail；能避免管道就保留原命令退出码。确实需要 pipefail 时，显式使用支持它的 shell，并确认镜像/agent 提供该 shell。不能把 `set -o pipefail` 无条件放进 `/bin/sh` 脚本。

## 7. 首启导入重复、缺数据或迁移互相冲突

数据库不存在、文件为空和 schema 版本落后是不同状态。多个副本、重启、失败半完成都可能让“首次启动”判断失效。

迁移/种子改成明确的单次协调步骤，使用项目已有迁移记录、幂等性和并发控制；生产操作先确认备份、数据来源、权限与恢复路径。不要自动 schema push、清库或导入演示数据。

跨数据库 dump 转换尤其需确认列名、类型、转义、时区与外键语义；位置式 INSERT 可能静默错列。不能用通用字符串替换器证明转换正确；需转换专用测试、行数/关键约束校验与事务边界。复杂数据迁移不属于部署脚手架的自动默认功能。

## 8. Compose unhealthy 或容器循环退出

区分“进程退出触发 restart policy”和“进程仍存活但 healthcheck unhealthy”；后者本身不会让普通 Docker restart policy 重启容器。

核对容器状态、退出码、日志、healthcheck 命令是否在镜像中可用、端口/路径是否真实。慢初始化时配置合理 start_period；不要靠放宽健康检查掩盖启动失败。依赖服务启动不等于已就绪，运行期仍需重试策略。

## 9. 端口、Ingress 或代理路由不通

分别核对监听地址、容器端口、Service targetPort、代理 upstream 和外部入口。`EXPOSE` 不等于进程监听或宿主发布。

Ingress API/class、pathType、正则和 rewrite 语义取决于集群与控制器。先确认 API 前缀是否保留，不从旧清单复制 rewrite 注解。NodePort 可不指定，让集群分配；扫描本地文件不能证明端口空闲。

域名、注册表、namespace、PVC 和 imagePullSecrets 必须来自已确认契约；没有权限时保留缺项，不访问另一个本机运维仓库补猜。

## 10. 静态前端改了容器 ENV 却没生效

先看变量在构建期还是运行期消费。静态资源已编译时，容器环境变量不会自动改包内 API URL。

沿用应用已有配置机制；新增运行期 config 文件时，应用必须实际读取，注意缓存与版本兼容。浏览器可读值不是秘密，不能把服务端 token 注入前端 bundle。

## 11. 发布失败后无法回滚

核对镜像版本是否不可变、旧镜像是否保留、配置是否可恢复，以及 schema 是否与旧程序兼容。`latest` 或清空历史可能让回滚不可重现。

代码、配置、数据分开规划回滚。数据库迁移不能靠切回旧镜像撤销；SQLite 的 Recreate 也不能替代正确卷配置、备份和恢复验证。
